# Backlog 作成スキル

ユーザーのプロンプトから内容をヒアリングし、**GitHub Issues** に Backlog アイテムを起票する。
このスキルの主たる利用者は **非エンジニア (ビジネス職 / PM / デザイナー)** であり、
作成された Backlog は後でエンジニアが `/indiehacker:refine` で Todo に分解する。

**スコープ**: このスキルは **Backlog の起票のみ** を担当する。実装タスクへの分解 (Todo 作成) は
`/indiehacker:refine` の責務で、ここでは行わない。実装手順や対象ファイルが明確で Todo として直接起票したく
なった場合も、まず Backlog として起票してから `/indiehacker:refine` に流す (背景情報が抜け落ちる事故を防ぐため)。

**最重要ゴール**: エンジニアが Backlog を読んだだけで「何を、なぜ、どこまでやるか」が
分かり、追加質問なしで `/indiehacker:refine` を始められる状態にすること。

**鉄則**: 推察・憶測で空欄を埋めない。ユーザーが明示的に答えていない項目は、
ヒアリングするか、`TBD` として §「不明点の扱い」の手順で残す。

**Why:** Backlog は「ユーザーが言ったこと」の正本。Claude の推測が紛れると、
ユーザーが自分の発言と勘違いしてレビューを通し `/indiehacker:refine` の前提が狂う。

## 手順

### 1. ヒアリング

非エンジニアの「やりたい」は曖昧なことが多い。エンジニアが認識齟齬なく実装に着手できるよう、
**A. 背景・課題 / B. 仕様・達成条件 / C. 参考資料** の 3 観点でヒアリングする。

#### 質問ツールの使い分け (必須)

- **`AskUserQuestion` ツールを使う**: 選択肢が 2〜4 個に絞れる質問 (例: 「全件出力 / フィルター結果のみ」「PC のみ / モバイルも」)。
  選択肢として提示すると、非エンジニアが「何を答えれば良いか」を即理解でき、回答ブレが減る。
- **テキストで質問する**: 自由記述が必要な質問 (背景・困りごと・参考 URL の有無 等)。

複数の論点を 1 ターンで聞く場合、選択肢型を `AskUserQuestion` で複数並べ (最大 4 問)、自由記述は
別途テキストで聞く。

#### 質問の絞り込み方

- ユーザー入力で十分埋まっていれば質問しない (例 2 参照)。不足分のみ 1 ターンで聞く。答えやすい具体例や選択肢を添える。
- 「読み取れた」とみなせるのは**ユーザーが明示的に書いた / 答えた項目のみ**。文脈から推測しただけのものは確認質問に回す。
- 重要度の高い項目 (誰が困っているか / 完了の定義 / スコープ外) で空欄が残るなら、質問数が増えても聞く。
- ユーザーが「分からない / 任せる」と答えた項目は `TBD` として §「不明点の扱い」の手順で残す。代案を本文に書き込まない。
- 業界の常識・他社事例を**達成条件に書きたくなったら質問に変換する**。例: 「CSV エクスポートが欲しい」だけなら、「UTF-8 BOM 付き」と決めつけず文字コードを質問する。

#### A. 背景・課題 (なぜやるのか)

ユーザーストーリーの「なぜ」を明確にするために必要。

- **誰が困っているか**: 想定ユーザーの役割 (例: 購入者 / 経理担当者 / 管理者)
- **今は何ができない / 何が辛いか**: 現状の課題、回避策の有無
- **なぜ今やるのか**: 事業インパクト、期日、関連する施策やキャンペーン
- **やらない選択肢はないか**: 既存機能で代替できないか、優先度の妥当性

#### B. 仕様・達成条件 (何をどこまでやるのか)

「達成条件」が曖昧だと `/indiehacker:refine` で詰める手戻りが発生する。

- **ユーザーの操作の流れ**: どの画面から入って、何をして、どうなれば成功か
- **完了の定義**: チェックリストで「〜できる」「〜が表示される」を列挙
- **エッジケース**: エラー時 / データなし / 権限なし / 同時実行 などの想定挙動
- **スコープ外**: 「今回はやらない」ことを明記する (将来やるなら別 Issue として起票)

#### C. 参考資料 (どんなイメージか)

イメージ素材はエンジニアの想像補完を助け、認識齟齬を最小化する。
ヒアリング時に **必ず 1 度は聞く** (なくても作成は可能だが、あると精度が上がる)。

**ユーザーへの聞き方の注意**: 「期待する成果物はありますか?」のような抽象語は使わない。
非エンジニアは「成果物」「要件」と聞かれても判断できないため、不足している素材を
**具体名で聞く** (全カテゴリを機械的に列挙しない)。

- **デザイン**: Figma / Sketch / 手書きスケッチの写真 / 画面のスクリーンショット
- **似たサービス**: 「〜のこの画面と同じ感じ」と言える URL や画像
- **社内ドキュメント**: Notion / Slack のスレッド / 過去 Issue
- **データの例**: CSV や Excel のサンプル / API レスポンス例 / モックデータ
- **運用ダッシュボード**: 不具合系で関連するログ管理画面の URL (例: SendGrid Activity / Stripe Dashboard) — エンジニアが調査時に即アクセスできる

**外部サービス・SDK が関わる場合は Claude 側で能動的に公式ドキュメント URL を取得する**
(必須): 不具合系・外部 API 連携系のタスクでは、関連サービスの公式ドキュメント URL を
ユーザーに聞くか、回答が得られない場合は **`WebSearch` で取得** して
「💭 イメージ・参考資料」に貼る。エンジニアの初動調査の出発点になる。

例 (Stripe 決済 + SendGrid メールの不具合系タスク):
- Stripe Webhook (`payment_intent.succeeded`) ドキュメント: https://docs.stripe.com/api/events/types#event_types-payment_intent.succeeded
- SendGrid Event Webhook (delivered / bounce / dropped) ドキュメント: https://www.twilio.com/docs/sendgrid/for-developers/tracking-events/event

**Why:** Backlog 起票時点で外部仕様の出典が並んでいると、エンジニアが `/indiehacker:refine` 着手前に
「自分で URL を探す」フェーズを飛ばせる。記憶の片隅にあるサービス名 (SendGrid 等) を
ユーザーが書いていれば、それだけで Claude は十分検索キーを組める。

### 2. Backlog 本文の組み立て

Backlog テンプレートの正本は **org 共通リポジトリ `<owner>/.github` の `.github/ISSUE_TEMPLATE/backlog.md`**（`<owner>` は対象リポジトリの owner。org 名はハードコードせず実行時に導出する）。GitHub の default community health files の仕様どおり、**対象リポジトリに自前のテンプレートがあればそちらが優先**され、無い場合に org 共通テンプレートが適用される。org 共通テンプレートはワーキングツリーに存在しないため、`Read` ではなく以下で取得し、その構造に従う:

```bash
# ローカル (リポジトリ固有) のテンプレートが最優先。無ければ org 共通テンプレートを取得する。
TEMPLATE=$(ls .github/ISSUE_TEMPLATE/backlog.md 2>/dev/null | head -1)
if [ -n "$TEMPLATE" ]; then
  cat "$TEMPLATE"
else
  OWNER=$(gh repo view --json owner -q .owner.login)
  gh api -H "Accept: application/vnd.github.raw" \
    "repos/${OWNER}/.github/contents/.github/ISSUE_TEMPLATE/backlog.md"
fi
```

取得に失敗した場合 (ネットワーク断・`gh` 未認証など) のみ、以下の節で定義するセクション構成をそのまま使う。

#### セクションの担当範囲 (必須)

テンプレートのセクションのうち、**`/indiehacker:issue` が埋めるのは起票時点で分かるものだけ**。
後続工程が埋めるセクションは **見出しごと残し、中身は空のまま** にする (プレースホルダの HTML
コメントも消さない)。

| セクション | 埋める工程 | このスキルでの扱い |
| --- | --- | --- |
| 🏁 ユーザーストーリー | `/indiehacker:issue` | ヒアリング結果を書く (必須) |
| 🎯 達成条件 (機能要件) | `/indiehacker:issue` | ヒアリング結果を書く (必須) |
| 📌 スコープ外 | `/indiehacker:issue` | ヒアリング結果を書く (推奨) |
| 💭 イメージ・参考資料 | `/indiehacker:issue` | §C で集めた素材を貼る (任意) |
| 🔍 `/indiehacker:refine` で確認したいこと | `/indiehacker:issue` | ユーザーが判断を委ねた項目のみ (任意) |
| 💭 期待する成果物 | `/indiehacker:refine` | **空のまま残す** |
| 📚 実装計画 | `/indiehacker:refine` | **空のまま残す** |

**Why:** `💭 期待する成果物` (ファイル単位の成果物 / Artifact URL) と `📚 実装計画` は、
`/indiehacker:design` の承認済み設計と `Plan` エージェントの出力を前提にしたセクション。
起票時点で Claude が推測で埋めると、`/indiehacker:refine` が「これはユーザーの要望か Claude の
想像か」を判別できなくなり、§「不明点の扱い」の鉄則 (推察で空欄を埋めない) に反する。

#### タイトル (必須)

タイトルは **「ユーザーが何をできるようになるか」を述語形式で書く** (`〜できるようにする` /
`〜を表示する` / `〜の不具合を修正する` 等)。`〜の機能を追加` / `〜の対応` のような
「実装行為」を主語にした言い回しは避ける。

書式: `<絵文字> <対象 + 述語>`

- 「対象」 = どの画面 / どのデータ / どのサービスか (例: 会員管理画面 / 顧客リスト CSV / 支払い完了メール)
- 「述語」 = ユーザーが何をできるようになるか (例: エクスポートできるようにする / 表示できるようにする)

**Why:** Backlog の一覧 (GitHub Issues タブ / Project ボード) で、非エンジニアでも
「**そのタスクで何が変わるか**」を一目で判別できるようにするため。「機能を追加」だけだと
何のデータ・どの画面の機能なのかが伝わらず、優先度判断・重複検知がしづらい。
絵文字も併用することでカテゴリが直感的に伝わる。

良い例:
- `✨ 経費申請の承認状態を一覧で確認できるようにする`
- `📤 会員管理画面で顧客リスト CSV をエクスポートできるようにする`
- `🎨 ログイン画面の UI を改善する`
- `🐛 支払い完了メールが届かない不具合を修正する`
- `🔒 会員管理画面でログイン履歴を表示できるようにする`
- `🔒 二要素認証でログインできるようにする`

NG 例 (実装行為が主語 / 対象が曖昧):
- ❌ `📤 会員管理画面に CSV エクスポート機能を追加` (何の CSV か不明)
- ❌ `🔒 ログイン履歴機能の追加` (どこで / 誰が使えるか不明)
- ❌ `🐛 メール配信周りの対応` (何の問題かが見えない)

絵文字の選び方 (代表的な分類。網羅ではないので、タスクの目的・対象に最も近いものを選ぶ):

- **新機能の追加**: ✨
- **UI / デザイン改善**: 🎨
- **不具合の修正**: 🐛
- **データのエクスポート / ダウンロード**: 📤
- **データのインポート / アップロード**: 📥
- **検索 / フィルター**: 🔍
- **通知 / メール**: 🔔 / 📧
- **認証 / セキュリティ / 権限**: 🔒
- **決済 / 課金**: 💳
- **レポート / 分析 / ダッシュボード**: 📊
- **パフォーマンス改善**: ⚡
- **モバイル対応**: 📱
- **多言語化 / 地域対応**: 🌐
- **アクセシビリティ**: ♿
- **ドキュメント整備**: 📝
- **API / 外部サービス連携**: 🔌

該当する分類がない場合は、タスクの目的・対象から **直感的に意味が通じる絵文字を 1 つ** 選ぶ。
迷ったら `✨` (新機能) を使う。複数の絵文字を並べず 1 つに絞る (タイトルの可読性のため)。

#### 🏁 ユーザーストーリー (必須)

テンプレートの指示どおり **【困りごと・背景】/【実現したいこと】/【期待するユーザー体験】の
3 ブロック** で書く。【期待するユーザー体験】は `〇〇として、△△したい。なぜなら□□だからだ。`
の形式にする。

```markdown
### 🏁 ユーザーストーリー

【困りごと・背景】
経理担当者は月末締めで経費承認を行うが、申請ごとに個別画面を開く必要があり 1 時間以上かかっている。

【実現したいこと】
経費申請の承認状態を一覧で確認・操作できるようにしたい。

【期待するユーザー体験】
経理担当者として、承認待ちの申請を一覧でフィルタできる。なぜなら、月末の作業時間を半分以下に
削減したいからだ。
```

視点が複数ある場合 (例: セキュリティ担当者と管理者) は、3 ブロックのセットを視点ごとに繰り返す。

**短く・シンプルに保つ** (必須): ユーザーストーリーは非エンジニアやそのタスクについて
詳しくない人でも 30 秒で理解できる粒度にする。**業務的な「なぜ」だけに絞り、技術仕様
(UTF-8 BOM 付き / SendGrid Event Webhook / 日次バッチ 等) や画面要素の列挙は
書かない**。それらは `🎯 達成条件` または `💭 イメージ・参考資料` に書く。

**「なぜなら」には具体事象 (数値 / 頻度 / 現状運用の困りごと) を 1〜2 文** 入れる。
「週に N 件問い合わせがある」「現状は X に Y 分かかる」のような事業的な背景は
ストーリーの説得力に直結する。

**Why:** ストーリーが長くなると、レビュアー (PM / ビジネス職) が「このタスクで何を
解決したいのか」をストーリーから読み取れず、達成条件と背景の対応がつかなくなる。
具体仕様を混ぜると「これはストーリーの一部か達成条件か」が読み手に判別できない。
別セクションに住み分けてストーリーは「課題の輪郭」のみに留める。

例 (複数視点 / 具体事象を 1〜2 文で):

> 【困りごと・背景】
> セキュリティ担当者は不正ログイン疑いの通報を受けた際に対象会員のログイン状況を確認したいが、
> 現状はログイン日時しか記録されておらず、不正ログインかどうかの初動判断ができない。
> セキュリティ担当者が不在のタイミングでは、管理者が一次対応するケースもある。
>
> 【実現したいこと】
> 会員のログイン履歴を確認できるようにしたい。
>
> 【期待するユーザー体験】
> セキュリティ担当者として、対象会員のログイン履歴を確認できる。なぜなら、不正ログインかどうかを
> その場で判断したいからだ。
> 管理者としても同じ画面から閲覧できる。なぜなら、セキュリティ担当者の不在時に一次対応したいからだ。

NG 例 (技術仕様や画面要素が混入している):

> 【期待するユーザー体験】
> 営業担当者として、CSV をエクスポートしたい。
> なぜなら、Excel で開いた際に日本語が文字化けすると分析資料として使えないため、
> UTF-8 BOM 付きで出力する必要があり、また現状はフィルター結果のみのダウンロードが
> できないため画面右上にボタンを配置して... ❌

→ `UTF-8 BOM` / `画面右上にボタンを配置` は技術仕様で、`🎯 達成条件` に書くべき。
【期待するユーザー体験】は「営業担当者として、画面で絞り込んだ顧客リストを Excel で分析できる。
なぜなら、現状はリストを手作業で写す必要があり、月次の分析業務に時間がかかっているからだ。」
程度に留める。

#### 🎯 達成条件 (機能要件) (必須)

チェックリスト形式 (`- [ ]`) で、**達成したい振る舞い (要件) のみ** を書く。
「動く」「使える」のような曖昧な表現は避ける。

**先頭行はユーザー体験ベース** で書く (ユーザーストーリーが解決する core 体験を 1 行目に置く)。

**実装手段を達成条件に書かない** (必須): 「日次バッチで削除される」「TTL で自動削除」のように
**実装手段が混じった書き方を避ける**。要件として「自動削除される」だけを書き、実装手段
(日次バッチ / TTL / タスクキュー 等) は実装者の設計判断に委ねる。

**UI 詳細・データ項目・表示レイアウトは達成条件ではなく `💭 イメージ・参考資料` に書く**
(必須): 達成条件には「ユーザーが何をできる / 何が起きる」(振る舞い) のみを書く。
「タブが追加されている」「1 件あたり N 項目が表示される」のような UI 構造の宣言や
データ項目の列挙は `💭 イメージ・参考資料` に Markdown table / 箇条書きで切り出す。

**Why:** 達成条件は「実装が完了したかを外部から検証できる粒度」のもの。実装手段や UI
構造を書いてしまうと、設計・リファインメントで「日次バッチではなく TTL の方が良い」
と判断したときに達成条件まで書き換える羽目になる。要件と実装の分離は、レビュー時の
「これは仕様か実装か」の混乱を防ぐ。UI 詳細は表で書いた方が直感的に伝わるので、
参考資料側に置くと達成条件のチェックリストも短く保てる。

例 (要件のみ・実装手段なし):
- [ ] 経理担当者として、画面遷移なしに全申請の承認状態を 1 画面で確認できる
- [ ] 承認状態 (承認待ち / 承認済み / 却下) で絞り込みできる
- [ ] 承認待ちが 0 件の場合に、その旨が分かる表示になる

NG 例 (実装手段 / UI 構造が混入):

- ❌ `- [ ] 経費申請一覧画面に「ステータス」カラムが追加されている` (UI 構造の宣言 → 参考資料へ)
- ❌ `- [ ] バッジコンポーネント (緑 / 黄 / 赤) でステータスを表示する` (UI 詳細 → 参考資料へ)
- ❌ `- [ ] 30 日経過したデータは日次バッチで削除される` (実装手段 → 「自動削除される」に)
- ❌ `- [ ] Redis に TTL 30 日でキャッシュする` (実装手段 → 「30 日経過後はアクセス対象外」に)

#### 📌 スコープ外 (推奨)

ヒアリングで「今回はやらない」と整理した項目を明記する。スコープの肥大化と認識齟齬を防ぐ。
将来やる予定があるものはここで言及しつつ、別 Backlog として起票することを促す。

**主課題と文脈が繋がる項目のみ書く** (必須): スコープ外を書く前に、その項目が
「ユーザーストーリーで述べた中心課題と関連した派生スコープか」を確認する。文脈が
本タスクの中で全く出ていない話題 (例: 配信不具合修正タスクで「メール本文のデザイン」)
は、ユーザーが入力で「スコープ外として」と添えていても **書かない**。

**Why:** 文脈の薄いスコープ外項目を並べると、Backlog を読んだエンジニアが「この
タスクはデザイン要素も含むのか?」と無用な認識を持ち、`/indiehacker:refine` の前提が拡張される。
スコープ外は「中心課題の派生で書き手も含めて誰かが拡大解釈しそうな範囲」を抑える
ためのもので、関係ない話題まで列挙する場ではない。

例 (CSV エクスポート機能の場合):
- 一括承認機能は今回スコープ外 (次フェーズで検討) ← 機能拡張の派生として妥当
- モバイル端末での操作は対象外 (PC のみ対応) ← 利用環境の派生として妥当
- 出力項目をユーザー側で選択する機能は対象外 (全項目固定) ← 入力仕様の派生として妥当

書かない例 (CSV エクスポート機能の場合):
- ❌ メール送信機能は今回スコープ外 (CSV エクスポートにメール送信の文脈は無いため)
- ❌ ログイン履歴は今回スコープ外 (CSV エクスポートにログイン履歴の文脈は無いため)

#### 💭 イメージ・参考資料 (任意)

§C で集めた素材をそのまま貼る。加えて、`🎯 達成条件` から切り出した **UI 詳細・データ
項目・表示レイアウト** をここに置く。

書き方の例:

- **UI 構成 (画面に追加するもの)**: 箇条書きで「会員詳細画面に『ログイン履歴』タブを追加」のように記述
- **表示項目**: Markdown table でカラム名 + サンプル値を示す
- **画面遷移・配置**: 簡単なスケッチ (ASCII / Mermaid / 言葉) で示す
- **外部ドキュメント URL** (§C で言及): RFC / SDK / API リファレンス
- **既存実装の参照**: 「現状の送信経路: Stripe Webhook → SendGrid (5 分以内)」のような現状把握

例 (ログイン履歴の表示項目):

| ログイン日時 | IP アドレス | User-Agent | 結果 | 失敗理由 |
| --- | --- | --- | --- | --- |
| 2026-05-15 10:23:14 | 203.0.113.42 | Mozilla/5.0 ... | 成功 | - |
| 2026-05-15 10:22:48 | 203.0.113.42 | Mozilla/5.0 ... | 失敗 | パスワード誤り |

**Why:** 達成条件から UI 詳細を分離すると、達成条件のチェックリストが短くなり、
エンジニアが「実装が完了したか」を検証しやすくなる。UI 詳細は表 / 図 / 例で示した方が
レビュアー (PM / デザイナー) にも直感的に伝わる。

#### 不明点の扱い

**原則: 仕様判断を要する項目は起票時にヒアリングし、達成条件 / スコープ外に反映する**
(必須)。`🔍 /indiehacker:refine で確認したいこと` セクションに大量の論点を残すのは **失敗パターン** で、
ユーザー (非エンジニア) が後で `/indiehacker:refine` 実行時にエンジニアと再度ヒアリングを行う羽目になり、
Backlog 起票の意義が薄れる。

ヒアリングの徹底:
- ユーザーストーリーで述べた中心課題に関わる項目 (権限範囲 / 件数上限 / 監査ログ要否 / 表示順 / ページネーション / 表示先画面 等) は、**起票時に `AskUserQuestion` で聞ききる**。
- 答えがあったものはそのまま **達成条件 / スコープ外** に書き込む。`/indiehacker:refine で確認したいこと` に逃がさない。
- ユーザーが「分からない / 任せる」と明示的に答えた項目のみ、`/indiehacker:refine で確認したいこと` に残す。

`🔍 /indiehacker:refine で確認したいこと` に書いて良いのは:
- ユーザーが明示的に「**判断を委ねる / 後で考える**」と答えた項目
- ユーザーがアクセスできない技術判断 (例: 「DB スキーマ移行が必要か」「キャッシュ層を挟むか」)
- 文字通り **本人にも判断材料がなく回答不能** だった項目

書かない:
- ユーザーに聞けば即答できる仕様判断 (権限・件数・運用フロー等)
- Claude が勝手に思いついた追加検討項目 (「将来こうなるかも」系の想像)
- 既に達成条件 / スコープ外に書いた内容の再掲

**Why:** Backlog は「起票時点でユーザーが言ったこと」の正本。`/indiehacker:refine で確認したいこと` が
肥大化すると、エンジニアが /indiehacker:refine で「ユーザーが何を望んでいるか」を再構築するコストが高く、
Backlog 起票が単なる「思いつき投稿」になってしまう。ヒアリングを起票時に尽くすことで、
エンジニアは Backlog だけ読めば仕様判断ができる状態を作る。

例 (CSV エクスポート機能の場合の正しい運用):

ヒアリング前に Claude が「これは聞かないと埋まらない」と判定する項目:
- エクスポート可能なユーザー権限 (営業のみか / 管理者も含むか)
- 件数上限 (同期で何件まで OK か)
- 監査ログ要否
- ファイル名のフォーマット

`AskUserQuestion` で聞いてユーザーが「営業と管理者の両方」「1,000 件まで」「監査ログ必要」
「ファイル名は `members_YYYYMMDD.csv`」と答えた場合、**達成条件に直接書く**:

```markdown
### 🎯 達成条件 (機能要件)

- [ ] 営業担当者または管理者として、画面に表示中の顧客リストを CSV としてダウンロードできる
- [ ] CSV のファイル名は `members_YYYYMMDD.csv` (例: `members_20260315.csv`)
- [ ] 1 回のダウンロードで出力できる件数の上限は 1,000 件
- [ ] エクスポート操作は監査ログに記録される (実行ユーザー / 実行日時 / フィルター条件)

### 📌 スコープ外

- 1,000 件を超える顧客リストの一括エクスポート (暫定対応のため、必要になった時点で別 Backlog)
- 営業 / 管理者以外のロール (CS / 経理 等) へのエクスポート権限付与
```

ユーザーが「ファイル名は任せる」と答えた **その項目のみ** `/indiehacker:refine で確認したいこと` に残す:

```markdown
### 🔍 /indiehacker:refine で確認したいこと

- [ ] ファイル名のフォーマット (ユーザーは任せると回答。命名規則の社内標準があるか確認)
```

### 3. プレビューと確認

**重要: 作成前に必ずプレビューを表示し、ユーザーの承認を得ること。**

タイトルと本文をまとめて表示し、以下を自己チェックする:

- [ ] タイトル先頭にタスク内容を表す絵文字が 1 つ付いているか (§「タイトル」参照)
- [ ] タイトルが「ユーザーが何をできるようになるか」の述語形式で書かれているか (「〜の機能を追加」になっていないか)
- [ ] ユーザーストーリーが **【困りごと・背景】/【実現したいこと】/【期待するユーザー体験】の 3 ブロック** で書かれ、「誰が」「何を」「なぜ」が揃っているか
- [ ] ユーザーストーリーが **30 秒で読み切れる粒度** か (技術仕様 / 画面要素 / 列挙が混入していないか)
- [ ] 【困りごと・背景】と【期待するユーザー体験】の「なぜなら」に具体事象 (数値 / 頻度 / 現状運用) が **1〜2 文で** 埋め込まれているか
- [ ] 達成条件の **先頭にユーザー体験ベースの 1 行** があるか (画面要素から書き始めていないか)
- [ ] 達成条件は外部から見て検証可能か (具体的な動詞で書かれているか)
- [ ] 達成条件に **実装手段** (日次バッチ / TTL / バッジコンポーネント 等) が混入していないか
- [ ] **UI 詳細・表示項目・データ構造** は達成条件ではなく `💭 イメージ・参考資料` に書かれているか
- [ ] スコープ外の項目は **すべて中心課題と文脈が繋がっている** か (文脈の薄い項目を機械的に列挙していないか)
- [ ] 参考資料を聞いたか (聞いて「ない」と言われた場合は OK)
- [ ] 外部サービス・SDK が関わる場合、公式ドキュメント URL を「💭 イメージ・参考資料」に貼ったか (`WebSearch` で取得して OK)
- [ ] `🔍 /indiehacker:refine で確認したいこと` に書いた項目は **ユーザーが明示的に「任せる」と答えたもの** か、本人にも判断材料がない項目に限られているか (Claude が勝手に思いついた検討項目を残していないか)
- [ ] `💭 期待する成果物` / `📚 実装計画` を **空のまま残している** か (`/indiehacker:refine` の担当セクションを推測で埋めていないか)
- [ ] エンジニアが追加質問なしで `/indiehacker:refine` を始められそうか
- [ ] 本文の各記述がユーザー回答に基づくか。推察で書いた箇所が残っていれば、本文から外して `### 🔍 /indiehacker:refine で確認したいこと` に移す。

ユーザーが承認したら次のステップへ。修正要望があれば調整する。

### 4. GitHub Issue の作成

`gh` CLI で作成する。本文は改行を保つため、**まず `Write` ツールで一時ファイルに書き出してから** `--body-file` で渡す:

1. `Write` ツールで、ユーザーが承認した本文を `/tmp/backlog-body.md` に書き出す。
2. Issue を作成する（`backlog` ラベルが未作成のリポジトリでは `gh label create` が必要なので、失敗したら作ってから再実行する）:

```bash
gh issue create --title "{絵文字} {タイトル}" --label backlog --body-file /tmp/backlog-body.md \
  || { gh label create backlog --description "リファインメント前の要望" --color ededed &&
       gh issue create --title "{絵文字} {タイトル}" --label backlog --body-file /tmp/backlog-body.md; }
```

GitHub MCP サーバーが使える環境なら `mcp__github__issue_write` でもよいが、`gh` を既定とする（このプラグインの他スキルはすべて `gh` を使っており、MCP サーバーは前提にしていない）。

- **タイトル**: §「タイトル」のルールに従い、先頭に絵文字を付ける (例: `✨ 経費申請の承認状態を一覧表示`)
- **ラベル**: `backlog` を設定する (ステップ 2 で取得した Backlog テンプレートの frontmatter と一致)
- **本文**: ステップ 2 で取得した Backlog テンプレートの構造に従って Markdown で記述する

### 5. 結果の報告と次のアクション案内

作成した GitHub Issue のリンクをユーザーに報告する。次のステップとして以下を案内する
(Claude が自動判定はせず、エンジニアの判断に委ねる):

- **実装イメージがある** (使用技術 / 成果物が明確) → `/indiehacker:refine` でタスク分解
- **実装イメージがない** (RFC 準拠 / 未経験のサービス連携 / ドメイン用語が未定義 等) → まず調査・プロトタイプでドメイン理解を深めてから `/indiehacker:refine` に進む

## ヒアリング例

### 例 1: 曖昧な要望から Backlog を作る

ユーザー入力:
> 「ユーザーがもっと使いやすいログイン画面にしたい」

Claude のヒアリング:
> 内容を Backlog として起票するために、以下を教えてください 🙏
>
> **A. 背景・課題**
> 1. 「使いやすくない」と感じた具体的なきっかけはありますか? (例: 問い合わせが多い / 離脱率が高い / ユーザーテストでの指摘)
> 2. 想定しているユーザー層を教えてください (例: 法人管理者 / 一般会員 / 高齢層)
>
> **B. 仕様・達成条件**
> 3. 「使いやすい」を実現する具体策のイメージはありますか? (例: ソーシャルログイン追加 / パスワードレス / UI のシンプル化)
> 4. この施策が成功したと言える指標はありますか? (例: ログイン完了率 X% 改善)
>
> **C. 参考資料** (1 つでもあれば添付してください)
> 5. 似たログイン画面 (他社サービスの URL / Figma / 手書きスケッチ / 過去 Notion など) で参考になるものはありますか?

### 例 2: 既に十分な情報がある場合

ユーザー入力:
> 「会員管理画面に CSV エクスポート機能が欲しい。営業が顧客リストを Excel で分析したいから。
> 全項目を出力して、UTF-8 BOM 付きで Excel が文字化けしないようにしたい」

Claude のヒアリング: (情報が揃っているため最小限)
> 1 点だけ確認させてください。エクスポート対象は **画面で表示中のフィルター結果のみ** ですか、
> それとも **全件** ですか? (ボタン配置に影響します)
